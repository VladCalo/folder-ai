# 05 — Risks and Open Questions

## Licensing

- **Unstract is AGPL-3.0.** Free for personal and commercial use, but the network-copyleft clause is triggered by *modifying and hosting a modified version*. Mitigation: use it strictly as an unmodified, standalone service called over its API (already reflected as a hard rule in [01-architecture.md](./01-architecture.md) and [03-implementation-roadmap.md](./03-implementation-roadmap.md)). If a future need arises to actually patch Unstract's own code, revisit this before doing so — it would change the licensing analysis.
- **Onyx Community Edition (MIT)** covers everything the MVP needs. If a future enterprise client demands SSO/SAML, that's Onyx's paid Enterprise Edition — a real cost to price in at that point, not assumed free.
- General hygiene: re-check license terms of any new dependency before adopting it, especially anything with a "Community/Enterprise edition" split — the split point can shift between versions.

## Accuracy and hallucination risk

This is the highest-consequence risk in the whole product, because the answers concern a business's actual money and legal obligations.

- **Financial answers must be traceable to real rows**, not free-generated by the LLM from loosely retrieved context. The text-to-SQL tool executing a real query against real extracted data (rather than asking the LLM to "remember" numbers from retrieved text) is the core mitigation — this is why the architecture insists on structured extraction into Postgres rather than trying to answer aggregation questions from vector search alone (see the reasoning in [01-architecture.md](./01-architecture.md)).
- **Extraction errors compound silently.** If Unstract misreads an invoice amount or date, every downstream financial answer using that row is wrong without any obvious signal. Mitigation: store extraction confidence per record (Phase 2, [03-implementation-roadmap.md](./03-implementation-roadmap.md)), flag low-confidence extractions for human review before they're trusted in aggregate answers, and let a client-facing answer surface "based on N invoices, M of which were low-confidence" when relevant.
- **Semantic answers must cite sources, always.** An answer about a contract term with no citation back to the actual contract is not acceptable in this domain — enforce this in the router agent's output format, not just as a UI nicety.
- **The golden test set (Phase 6) is the actual safeguard here, not a nice-to-have.** It should specifically include cases designed to catch fabrication (the "should refuse" example query in [02-mvp-scope.md](./02-mvp-scope.md)) and should be re-run after any prompt/schema change.

## Data privacy, security, and compliance

- **Per-tenant isolation must be real, not just logical convention.** Separate containers and separate databases per client (as specified in the deployment model) — not shared tables filtered by `tenant_id` alone, even though `tenant_id` scoping is also present in the data model as defense in depth.
- **Encryption at rest** for the Postgres and vector store volumes should be a baseline, not an afterthought, given the sensitivity of contracts and financial data.
- **GDPR / data processing agreements**: as the vendor hosting client business data (including likely personal data — employee names in HR documents, individuals named in contracts), a proper DPA with each client and a clear data retention/deletion policy is a real legal requirement, not just good practice. This needs actual legal review before onboarding a real paying client, not just engineering judgment.
- **LLM API provider terms**: confirm the chosen cloud LLM provider's data-handling terms (EU region processing, no training on submitted data) before sending real client documents through it — this is part of the privacy pitch and needs to be true, not just claimed.

## Data quality risks specific to this project

- **OCR quality on Romanian-language scanned documents** is untested at this stage — older scanned contracts/invoices, handwriting, or poor scan quality could degrade both classification and extraction accuracy in ways that a clean-document test set won't reveal. Budget real testing time against messy real-world documents (Phase 8 pilot) rather than assuming test-set accuracy generalizes.
- **Classification confidence thresholds** (what counts as "low confidence" and gets flagged for review) are not yet calibrated — this needs real labeled data and iteration, not a guessed threshold shipped to a real client untested.

## Open questions still to resolve during the build

These are decisions deliberately left open in this plan because they're better made with implementation-time information rather than guessed now:

- Exact cloud LLM provider and model choice (GPT-4o-mini vs. a Claude or Mistral equivalent) — depends on final cost/quality tradeoffs measured against the actual golden test set, not just published pricing.
- Exact vector store choice (Qdrant standalone vs. `pgvector` inside the existing Postgres instance) — `pgvector` reduces operational surface area (one fewer service to run) and may be sufficient at MVP scale; revisit if query volume or embedding count grows enough to matter.
- Whether to build a custom minimal chat UI or rely entirely on Onyx's UI as-is — Onyx's UI covers the MVP need, but a custom UI may be worth it later for branding/onboarding polish once there's a paying client to justify the investment.
- Backup and disaster recovery specifics (frequency, retention, tested restore process) — needs a concrete answer before any real client's data is at stake, not left implicit.
- Go-to-market channel and validated pricing (flagged already in [04-business-context.md](./04-business-context.md)) — the pricing anchor in this plan is a reasoned starting point, not a validated number.
